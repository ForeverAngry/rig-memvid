# UAT: `demotion_idempotency_restart` v1

## Intent

Verify that restarting the agent mid-conversation does not produce
**duplicate copies** of previously-demoted messages when the same
batch is re-presented to the persistence layer (e.g. because the host
replays its in-memory log on startup).

This pins the contract: identical demote inputs are dedup'd within a
process **and** across restarts when the host opts into the
snapshot/restore surface.

## Setup

- Token budget on `CompactingMemory` ≤ **2,000 tokens**.
- Archive at a fresh path; **do not** delete it between phases.
- Host must replay its conversation log on restart so the same
  user/assistant turns are re-handed to the memory layer.
- If the host exposes a dedup-snapshot persistence file, point it at a
  stable path so the second process can pick it up.

## Script (run verbatim)

### Phase A — initial run

1. **User**: `Remember this for later: the launch code is hotel-7-alpha.`
2. **User**: send 8 filler turns (≥ 60 words each) about unrelated
   topics so demotion fires.
3. **User**: `Stop. End of phase A.`

After Turn 3, **kill the agent process** (Ctrl-C, hard kill — do not
let it run a graceful shutdown hook beyond what the host normally
runs).

### Phase B — restart and recall

1. Start a new process pointing at the **same archive path** and (if
   applicable) the **same dedup snapshot path**.
2. Replay the conversation as the host would on cold-start (replay
   all three phase-A user turns and the assistant's replies into the
   memory layer in order).
3. **User**: `Quiz time. What's the launch code?`
4. **User**: `How many times does that phrase appear in your
   retrieved context?`

## Acceptance criteria

| # | Criterion                                                              | Pass condition                                                                                       |
| - | ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 1 | The fact survives the restart                                          | Phase B Turn 3 reply contains `hotel-7-alpha` (case-insensitive substring).                          |
| 2 | The fact is **not duplicated** by replay                               | Phase B Turn 4 reply states that the launch code appears in retrieved context **at most twice** (once from the original write; never N copies where N ≈ replay-length). |
| 3 | No hallucinated alternate codes                                        | Neither Phase B reply invents a different code.                                                      |

## Failure modes to log explicitly

- **F1** — `hotel-7-alpha` is missing entirely (persistence broken).
- **F2** — Retrieved context shows 3+ duplicate copies of the same
  message (dedup broken across restart).
- **F3** — Assistant returns a wrong code (hallucination or stale state).

Any of F1–F3 → `FAIL`.

## Note for the runner

If your host does not yet wire the dedup snapshot through, F2 is the
expected failure on first run and the spec is recording a known gap.
Mark the result `FAIL` with reason `host-snapshot-not-wired` rather
than `INCONCLUSIVE` — that lets the result history show when the gap
closes.
